변경 내용

적용 내용

처음에는 ‘자동 검증 프로그램’을 만들고, 그 위에 ‘AI QA 봇’을 붙이는 방식이 좋습니다. AI가 플레이하거나 화면을 살펴보고, 프로그램이 오류 여부를 판정하도록 역할을 나누면 결과를 믿고 활용하기 쉽습니다.

말씀하신 세 가지는 이렇게 구분할 수 있습니다.

형태 하는 일 적합한 용도
QA 프로그램 정해진 동작을 실행하고 기대 결과와 비교 반복 검사, 수정 후 문제 재발 확인
QA 봇 화면과 상태를 보고 다음 행동을 선택 다양한 경로 탐색, 예상 밖 상황 찾기
AI QA 테스터 요구사항을 읽고 검사 계획·실행·버그 보고까지 수행 넓은 범위의 QA 보조

현재 작업 중인 DotAction을 대상으로 생각하신다면, 다음 구성이 출발점으로 적합합니다. 게임 프로젝트인지는 아직 미확인이라, 아래는 게임을 가정한 예시입니다.

1. 먼저 검사할 행동 하나를 정합니다.

처음부터 “게임 전체를 테스트하는 AI”를 목표로 잡으면 문제가 생겼을 때 원인을 구분하기 어렵습니다. 예를 들어 다음처럼 시작합니다.

게임 실행 → 스테이지 진입 → 이동 → 공격 → 적 처치 → 결과 확인

각 단계에 성공 조건을 붙입니다. “공격 버튼을 눌렀다”는 실행 기록이고, “적 체력이 감소했다”가 검증 결과입니다.

2. 게임에 QA용 관찰·조작 통로를 만듭니다.

화면 인식만으로 모든 것을 판단하기보다, 개발 빌드에서 다음 정보를 읽고 행동을 실행할 수 있게 만드는 편이 정확합니다.

  • 관찰: 현재 씬, 플레이어 위치·체력, 적 수, 진행 상태, 오류 로그
  • 조작: 이동, 공격, 상호작용, 스테이지 초기화
  • 재현: 시작 상태와 난수 시드 고정, 입력 순서 기록

실제 키보드·마우스 입력 검증도 따로 필요하지만, 내부 상태를 함께 읽으면 “왜 실패했는지”까지 파악하기 쉬워집니다.

3. 판정은 명확한 규칙부터 만듭니다.

예를 들면 다음과 같습니다.

  • 벽을 통과하면 실패
  • 체력이 0인데 계속 행동할 수 있으면 실패
  • 완료 조건을 충족했는데 결과 화면이 나오지 않으면 실패
  • 제한 시간 동안 진행 상태가 바뀌지 않으면 멈춤 의심

화면이 이상하거나 조작감이 어색한 문제는 AI가 의심 사례로 모으게 하고, 확정 오류와 구분하는 것이 좋습니다.

4. 그다음 AI에게 탐색을 맡깁니다.

AI에게는 “아무거나 테스트해”보다 구체적인 목표를 줍니다.

“이 스테이지에서 이동 불가능한 상태를 찾아라. 발견하면 마지막 행동과 위치를 기록해라.”

구조는 다음 정도면 충분합니다.

대상 프로그램 ↔ 관찰·조작 인터페이스 ↔ QA 실행기 ↔ AI 탐색기

QA 실행기는 시간 제한, 초기화, 판정, 증거 저장을 담당하고 AI는 탐색할 행동을 선택합니다.

5. 결과물은 재현 가능한 버그 보고서로 만듭니다.

최소한 빌드 버전, 시작 조건, 재현 순서, 기대 결과와 실제 결과, 로그·화면, 재현 횟수가 남아야 합니다. AI가 발견한 경로를 저장해 다시 실행할 수 있어야 수정 여부도 확인할 수 있습니다.

제가 권하는 첫 완성 기준은 **“대표 시나리오 하나를 자동 실행하고, 실패하면 증거와 재현 순서를 저장한다”**입니다. 이후 시나리오를 늘리고 AI 탐색을 추가하시면 됩니다.

만드시려는 대상은 DotAction 같은 게임인가요, 웹·앱인가요? 그리고 주로 찾고 싶은 것이 기능 오류, 화면 문제, 플레이 중 버그 중 무엇인지 알려주시면 구현 구조를 구체적으로 잡아드리겠습니다.
