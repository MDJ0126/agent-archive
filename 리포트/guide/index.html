TRACEFOLIO · AUTHORING STANDARD V2

Tracefolio 게시물 작성 가이드

Codex 전역 지침에서 현재 공개 저장소의 지침을 목차와 함께 읽을 수 있습니다.

프로젝트 전용 지침 사항은 프로젝트별 작업 기준과 근거를 모아 봅니다. 작업 전 해당 원문을 확인하고, 작업 종료 시 검증된 교훈을 기존 항목에 통합합니다.

작업 시작 전에 작업 시작·반복 QA 메뉴얼을 읽고 작업 메뉴얼을 등록·갱신합니다. 최초 필요한 작업은 최대30개, 이후에는1~5개씩 반복하며 전체 미완료 목록과 QA 이력을 보존합니다. 메뉴얼 JSON 템플릿을 사용합니다.

작성 기준 v2 — 사람과 AI가 같은 폼·JSON·검사로 작성합니다. 프로젝트별 결과 보고서와 버그 보고서를 같은 기준으로 관리합니다. 글마다 별도 HTML·CSS를 만들지 않습니다.

보고서 작성 폼 · 5단계와 공통 JSON 설명 · 결과 JSON 템플릿 · 버그 JSON 템플릿 · JSON 스키마

1. 분류와 단계

등록한 프로젝트 ID와 로고를 사용합니다. 결과 분류·버그 5단계·재개·이력 기준은 처리 가이드에 있습니다.

2. 사람이 작성하는 방법

사이트의 보고서 작성 폼에서 프로젝트·분류와 실제 내용을 입력합니다. 검사·미리보기는 공통 데이터와 Markdown을 보여줍니다. 공개 내용을 확인한 뒤 GitHub에서 최종 제출합니다. GitHub 로그인이 필요하고 등록 이후 자동 검사·배포를 거쳐 사이트에 표시됩니다. 브라우저 임시저장은 그 기기에만 남는 초안이며 사이트 등록이 아닙니다.

3. AI가 작성하는 방법

결과·버그 JSON 템플릿을 실제 값으로 채워 같은 검사 함수를 호출하는 CLI를 사용합니다. 원본 JSON을 보존하지 않고 Markdown을 직접 만들어 필수 항목을 우회하지 않습니다.

node 리포트/create-report.mjs --input report.json --dry-run
node 리포트/create-report.mjs --input report.json
node 리포트/build.mjs
node 리포트/verify.mjs
node 리포트/verify-migration.mjs
node 리포트/verify-editorial.mjs
node --test 리포트/tests/*.test.mjs

GitHub 접수를 사용할 때는 같은 JSON을 tracefolio:v2 표시와 json 코드 블록으로 등록합니다. 사이트 폼도 같은 내용을 만듭니다. 구체적인 표시와 이벤트 처리는 공통 등록 설명을 참고하세요.

4. 반드시 기록할 내용

항목 기준
제목·요약 실제 결과나 문제를 구체적으로 설명합니다. 요약은 180자 이내입니다.
결과 끝난 일과 남은 일을 구분합니다. 구현·설치·실행·검증·배포를 하나의 완료로 묶지 않습니다.
버그 재현 환경·버전, 재현 순서, 기대 동작, 실제 동작을 작성합니다.
원인 검증한 원인만 씁니다. 확인하지 못했다면 미확인으로 남깁니다.
변경 내용 실제로 바꾼 내용과 이유, 변경 전·후를 설명합니다.
검증 실행한 대상·명령·결과와 범위를 기록합니다. 미실행·실패를 통과로 바꾸지 않습니다.
남은 사항 미확인·제한과 다음 행동을 기록합니다. 기록이 없다고 남은 일이 없다는 뜻은 아닙니다.
시간·검색 제안 시간, 실제 소요·완료 시각·시간대, XERJ 사용 근거를 기록합니다. 제공되지 않은 시간은 만들지 않습니다.

5. 생성되는 게시물 형식

프로젝트·보고서 분류·단계·우선순위
제목 / 요약 / 상태 / 날짜·버전
작업 결과
변경 내용 (버그: 재현 조건·순서·기대·실제·원인 포함)
검증
남은 사항
작업 시간
등록·상태 변경 이력

하나의 JSON 계약에서 format: tracefolio-v2 Markdown을 생성합니다. 빌드는 보존된 JSON을 재검사하고 Markdown이 같은 데이터에서 생성됐는지 확인합니다. 본문 H1 제목을 중복 작성하지 않습니다. 프로젝트별 최근 글을 참고하되 과거 v1·legacy 예외를 새 글 작성에 사용하지 않습니다.

6. 파일과 버전

projects/<project>/posts/       생성된 Markdown
projects/<project>/reports/     생성된 HTML
projects/<project>/assets/      JSON·로고·첨부
projects/<project>/originals/   원문 백업

GitHub로 접수한 글은 TF-이슈번호로 표시됩니다. 수정 시 새 버전과 단계 이력을 보존하고 목록에는 최신 버전만 표시합니다. 오래된 기록·이전 버전·원문은 지우지 않습니다. 제품 버전과 문서 버전은 구별합니다.

7. 읽기와 공개 기준

  • 한 문단에 하나의 결과나 근거를 쓰고 존댓말을 사용합니다.
  • 표는 비교·매핑·검사 결과에 사용하고 긴 코드는 코드 블록에 넣습니다.
  • 이미지에는 실제로 확인할 수 있는 내용을 설명하는 alt 문구를 씁니다.
  • 첫 화면에 전체 로그·파일 목록·해시를 나열하지 않고 필요한 근거와 링크를 둡니다.
  • raw HTML, script, iframe, 실행 URL을 사용하지 않습니다.
  • 인증정보·개인 로그·세션 기록·비공개 데이터를 공개 등록하지 않습니다.
  • 원문 시점의 테스트를 이번 작업의 검증으로 보고하지 않습니다.
  • 푸시와 배포 성공을 구분하고 공개 URL까지 확인한 뒤 완료라고 안내합니다.

과거 v1·legacy 글은 읽기 호환을 유지합니다. 이 글들의 숫자와 판단은 원문 시점의 기록이며 현재 상태를 새로 증명하지 않습니다.

프로젝트 소항목

턴룸의 소항목 ID 및 작성 폼 선택 기준은 처리 가이드의 프로젝트 소항목 절을 참고합니다.

결과 이미지 필수 첨부와 압축

촬영·전후 비교·압축 기준은 작업별 지침의 Tracefolio 절에 있습니다. 이미지는 projects/<project>/assets/에 저장하고 JSON 본문에 ![확인한 내용](../assets/압축파일.webp)로 넣습니다. 작성 폼도 같은 문법을 사용합니다. 로컬 경로는 공개 이미지 주소로 사용할 수 없습니다.

  • 결과 제출 전 변경 목록과 실제 전후 이미지 쌍을 대조합니다. 모든 작업을 포함한 블로그 글에 썸네일을 등록하고 공개 목록과 개별 글에서 표시를 확인합니다. 세부 기준은 작업별 지침의 Tracefolio 절을 따릅니다.

QA 토론 · 개선 제안 · 새 기능 요청

토론 종류·상태·원본 연결·결정 기준은 처리 가이드의 QA 토론 절을 참고합니다.

작업 메뉴얼 형식

메뉴얼의 작성·갱신과 QA 기록은 실행 메뉴얼을 따릅니다.

교훈 검토와 지침 반영

교훈의 근거·적용 범위·반영 여부는 작업별 지침의 교훈 반영 절에 따라 기록합니다.

단일 보고서의 TC별 원본 대조

여러 탭이나 기능을 하나의 결과 보고서에서 검증할 때는 결과 JSON의 선택 항목 testCases에 최대60개를 기록합니다. 보고서를 분할할 필요가 없습니다. 각 항목은 고유 id, group, title, 실행 steps, expected, actual, status를 포함합니다. 상태는 pass(통과), fail(실패), partial(부분 확인), not_run(미실행)입니다.

reference에 원본의 출처·버전·비교 범위를 적고, referenceImage·beforeImage·afterImage는 ../assets/ 아래 실제 이미지 경로로 지정합니다. 원본 또는 수정 후 화면이 없으면 missingEvidence에 사유를 명시합니다. fix와 retest에는 실제 수정·재검증을 기록합니다. 이미지를 만들거나 미실행을 통과로 채우지 않습니다. 모든 TC가 통과하기 전에는 전체 결과를 complete로 등록할 수 없습니다. 이 확장도 공통 H2 순서와 보존 JSON 검사를 그대로 사용합니다.

간결한 보고와 변경 전·후 비교

코드 수정 보고에는 완전한 핵심 함수·메서드를 넣고, 독립 실행 흐름마다 해당 조건에 맞는 Mermaid를 넣습니다. 작업별 지침의 Tracefolio 절에서 적용 조건, 실제 렌더링 확인, 본문 구성 및 전후 비교 기준을 확인합니다.

작업별 지침의 Affinity 전용 CLI 절을 참고합니다.

수정 범위별 전후 화면과 핵심 요약

각 수정의 전후 화면은 작업별 지침의 Tracefolio 절에 따라 짝지어 제공합니다.

보고서에 작업 대화 기록 함께 남기기

수록할 발언·인용·공개 전 가림 기준은 작업별 지침의 Tracefolio 절에 있습니다. 공통 H2 순서를 유지하며 JSON의 changes 등 해당 본문에 H3 ### 대화 기록으로 요약합니다. 긴 기록은 projects/<project>/assets/conversations/ 또는 같은 프로젝트의 별도 글로 분리해 링크합니다. 대화 접근에 제한이 있었다면 확인 범위와 누락을 적습니다.
